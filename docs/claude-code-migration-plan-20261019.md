## 1. 推荐结论

**推荐先修 3 个已复现问题，再迁移 6 组高收益能力，补强 2 组 Moss 已有能力。** 第一批应同时交付可靠性修复和队列完整回填，让收益可以直接感受到。Goal、Monitor 等持续执行能力进入后续试点，不阻塞日常体验改进。

六组主迁移是：**工具结果完整性与按需读取、消息撤回编辑、MCP 目录一致性、本地提示词诊断、有界重试及可选模型回退、运行资源预算**。两组增量增强是：**侧问及折叠后的交付可见性、现有自测的迁移验收场景**。

Moss 的 Workspace、Task list、Team/Boss/Coordinator、Workflow App、App SDK、Agent Mail、文件观察和 presentation 都继续使用。计划没有删除这些能力，也不另建第二份任务列表、结果面板、邮箱或工作流引擎。清理的对象只能是经验证被新实现替代的重复内部逻辑，必须在对应变更中单独列明。

## 3. 前置修复：与新增功能分开验收

### H1 搜索异常不得伪装成零结果

证据 A：[ripgrep.ts](../src/utils/ripgrep.ts) 的异常退出路径已用真实 `rg` 复现。迁移新版对“未完成搜索”的明确表达，保留 Moss 已有调用方式。

- 退出 0 = 成功；退出 1 = 完整执行后无匹配；退出 2、启动失败、权限错误、输出溢出和取消分别保留原因。部分 stdout 可以保留，但不能标成完整成功。
- 验收：正常/零匹配/非法正则/不可读路径/取消/部分输出；模型及 UI 看到同一个状态。不能只在低层抛错，再被上层 catch 转成 `[]`。

### H2 图片先限量读取，再解码/压缩

证据 A（受控读取探针，不是实测内存耗尽）：[FileReadTool](../src/tools/FileReadTool/FileReadTool.ts)、[fsOperations.ts](../src/utils/fsOperations.ts)。

- 在实际文件句柄读入环节限制字节；stat 仅是预检，不能取代读入上限。保留正常图片能力，异常类型和超过限制都明确报错。
- 覆盖文件增长、非常规文件/流、取消、解码失败；不采用“先完整读入再检查大小”。超大解码尺寸/像素数也需要在解码路径明确上限。
- 验收用小边界 fixture 和受控 I/O；无需创建巨大文件或进行破坏性内存测试。

### H3 小窗口模型能力必须生效

证据 A：[context.ts](../src/utils/context.ts) 当前忽略小于 100K 的有效 `max_input_tokens`，此前探针确认 65536 被算成 200000。[desktopModelContext.ts](../src/utils/model/desktopModelContext.ts) 当前已委托同一个解析函数，但 `isDefault` 仍有 100K 判断，应同步修正。

- 合法能力值必须参与计算；元数据缺失与非法值保留明确的默认标记。区分提供方的总窗口、输入上限、输出上限，计算可用输入时避免重复扣减。
- 不让 Claude 别名或 `[1m]` 在不支持的提供方上绕过能力边界。显式用户覆盖与可信能力冲突时使用明确配置语义，不能悄悄假设支持。
- 验收 32K/64K/128K/200K/1M、同名模型不同提供方、并发会话、大窗口切小窗口、无能力接口；压缩、Read 上限、ToolSearch、UI 使用同一口径。

### H4 Hook/权限改写参数后二次校验

实施状态：已用实际 permission resolver 源码的隔离用例复现缺口并修复。主工具路径覆盖 Hook 改写、权限回调改写、原地修改、最终参数的 deny/ask 规则、二次改写终止及取消；合法问答回填、permission UI 的内部 sed 编辑参数保留。详见可靠性批次交付；不把此范围扩展为全部第三方执行器的安全审计。

实施前证据 B：[toolExecution.ts](../src/services/tools/toolExecution.ts) 存在初始校验与后续 updatedInput，需用故障用例确认缺口。此次确认的是改写绕过最终校验的路径，没有将其描述为已发生的用户数据越权事件。

- 固定顺序：改写 → 规范化 → schema/工具约束校验 → 按实际执行参数核对权限 → 执行一次。权限决定绑定最终参数；若改写改变了已授权动作范围，沿用现有权限机制重新判断。
- 非法/保留字段、越界路径、权限阶段 updatedInput、合法问答回答/路径回填均覆盖；不无限循环 Hook，不静默去掉未知参数后继续产生副作用。

H1–H3 不必等待大范围重构；H4 是相关扩展生命周期增强的前置检查。

## 4. 六组主迁移的具体设计

### R1：扩展现有工具结果，给模型与 UI 同一份事实

落点：[Tool.ts](../src/Tool.ts)、[toolResultStorage.ts](../src/utils/toolResultStorage.ts)、[toolLimits.ts](../src/constants/toolLimits.ts)、现有 Grep/Glob/Read/WebFetch/Bash 工具和结果渲染器。参考上游 C01/C02/C06 与 SDK 字段变化。

**实现范围：**

1. 增加共享的、可选的结果元数据，在每个工具 adapter 映射；不要强行替换所有旧 payload。分别描述执行状态、数据完整性、已展示数、已知总数、分页位置、落盘字节和截断原因。后台任务的 `running` 不等于“完整结果”，无匹配与失败也不共用状态。
2. 无法完整计数时，总数未知；不得把“本页 100 条”当“总共 100 条”。计数被预算打断时返回统计不完整，不为了显示总数而无限扫描。
3. 大输出限制分三层：产生/采集、落盘单项与本次运行累计、送给模型的摘要。超限仍继续排空进程管道或按明确策略停止采集，避免子进程被阻塞；保留退出状态和有界尾部错误。持久化文件明确是全文还是片段，并输出可读取范围。
4. 采用 Moss 自己的限制配置。先沿用现有摘要阈值；新增落盘限额通过代表性日志 fixture 校准，不能照搬上游 1 GB。持久化预算只管理工具输出缓存，不删除 workspace 产物和用户编辑文件。
5. 小扩展按独立 PR：`Grep -o`；Read `allow_large`；WebFetch 续读位置。前者确认匹配片段、行、文件的计数单位；后两者依赖 H3 和结果边界。`allow_large` 是请求提高软上限，硬字节/上下文余量不足时仍拒绝或分页。
6. 网页续读绑定本次已取得内容的版本/引用，避免每页重抓后拼成不一致全文；缓存到期或内容变化应让模型重新取页。其行为适配 Moss 当前 WebFetch 实现，不硬套上游 offset 的内部单位。

建议的最小内部元数据契约如下，名称可在实施时适配已有类型，但含义应先固定：

| 字段 | 约束 |
| --- | --- |
| `version` / `toolUseId` | 关联既有工具调用；重试和历史恢复不重新发明一个调用身份 |
| `completeness` | `complete / partial / unknown`，描述本次查询范围内的数据完整性；执行失败/运行中沿用已有生命周期字段单独表达 |
| `counts` | 每项带 `unit`、`shown`、可选 `total` 和 `countIsComplete`；行数、文件数、匹配片段数不能混加 |
| `continuation` | 可选的资源/版本引用与位置；仅在确实能继续读取时返回 |
| `storage` | 可选的 Host 资源引用、`storedBytes`、可选 `originalBytes`、`truncatedAtBytes`/原因；原始总量没采完则未知 |

原始工具 payload 和 MCP 内容块保留。元数据在内部协议/历史中持久化，发给模型时通过该提供方允许的工具结果内容表达，不能向厂商 API 硬塞不支持的顶层字段。此契约不替代文件观察记录或 presentation 回执。

**默认/兼容：**旧工具调用仍合法；旧历史缺失完整性字段时显示“未记录/未知”，不补造 0 或完整成功。计数、状态、提示来自同一 adapter。文件变化卡片继续只依赖文件观察/展示资源，Bash 的结构化状态不能成为改动数量来源。

**验收：**H1 全部路径；超长单行及 Unicode 搜索；分页总数不完整；Read 余量不足；并发落盘超预算、磁盘失败、取消；截断 JSON 不能宣称是完整可解析 JSON；WebFetch 两次内容变化。旧会话可读，新结果在三种 Host 中语义相同。

**回滚：**可关闭新的阅读参数/分页入口；保留新字段的读取兼容。已截断内容无法恢复，不能在关闭功能后重新标为全文。错误修复与硬读取边界不能通过功能开关恢复为旧缺陷。

### R2：先完整回填，再解决确认与恢复

落点：[App.tsx](../ui/src/renderer-react/App.tsx) 的 `QueuedMessage`/`handleStop`/`handleRemoveQueuedMessage`、[chat-area.tsx](../ui/src/renderer-react/components/chat-area.tsx)、[moss-client.mjs](../ui/src/client/moss-client.mjs)、[agent-ipc.mjs](../ui/src/agent-ipc.mjs)、[session-send-cancellation.mjs](../ui/src/session-send-cancellation.mjs)。Core 已有 [messageQueueManager.ts](../src/utils/messageQueueManager.ts)，但不能把其模块级队列直接作为 Desktop 多会话共享队列。

**R2a，首批：**

- 增加“撤回编辑”，保留“移除”的明确含义。回填完整 composer 快照：文字、附件资源、选中 Skill、App 资源、intent、Agent 以及所属 session/workspace 版本。
- Stop 不再将多条消息拼成一段文字并丢弃元数据。待发送项以原有独立条目恢复；输入框空时可载入一条，其余保持可恢复草稿。输入框已有内容时不覆盖，提供恢复入口。

**R2b，后续：**

- 在现有发送协议中加入稳定客户端消息 ID 与修订号。客户端与宿主采用明确的发送状态机：`queued → dispatching → accepted → running → terminal`；另外区分 `withdrawn`、`failed` 和确认状态未知。前两项是客户端发送状态，后续以宿主记录为准；`accepted` 表示宿主已持久接收，不声称模型已经阅读。
- 由实际执行 Host 作为已接收项的权威源；UI 保存未接收草稿。调用执行器前提交接收记录，恢复时查询状态再协调。对同一 ID/修订号的重复发送返回原收据，内容不同则拒绝混用。
- 撤回用修订号比较并更新，若已开始执行返回 too-late，提供现有 Stop；不自动中断再重发。网络断开且接收情况未知时查询回执，不能生成新 ID 盲发。
- Web/remote-direct 能力协商：支持回执则使用；旧 Host 保留明确“接收状态未知/待核对”，不承诺跨崩溃恰好执行一次。写磁盘、发消息等副作用执行到一半的运行，恢复不能自动整轮重放。

**验收：**带附件/Skill/App 的两条排队消息逐条撤回；已有输入不丢；Stop 与 turn-end 同时发生；workspace 切换；Web 刷新与双窗口；已接收但回包丢失；同 ID 重复到达；Host 在接收前/执行中崩溃。核对产物/副作用实际次数。

**默认/回滚：**R2a 默认提供，未撤回的队列顺序不变。R2b 必须等 Host 和客户端兼容路径完成再开启；停用新发送入口仍应能读收据与草稿，不能删队列持久数据。

### R5：让等待有边界，再提供自选回退链

实施状态：R5a 已提供每个逻辑模型请求的默认等待额度（普通 120 秒、无人值守 600 秒）和硬尝试上限（12/20 次）；普通错误重试继续受既有 `maxRetries` 限制，无人值守 429/529 沿用其旧次数策略并受新的共享上限约束。流式、thinking 兼容调整与非流式恢复共享额度，已交付工具调用的响应禁止自动整条补发。额度约束重试等待，不替代单请求网络超时或 R6 顶层任务截止时间。R5b 尚未实施。

落点：[withRetry.ts](../src/services/api/withRetry.ts)、模型能力/路由、compact 调用和现有 `api_retry` 事件。当前已支持可取消等待和心跳，不重复实现。

**R5a：**为一次逻辑模型请求设累计等待预算和尝试上限，覆盖普通重试、persistent 模式、同请求的协议降级/非流式补发路径。使用单调时间计量；不得通过递归重新进函数清空预算。界面显示原因、已尝试次数、下次重试和截止状态。

推荐初始策略供 fixture 与真实网关校准：交互请求累计重试等待 120 秒、无人值守 600 秒；沿用现有每次请求超时并受顶层任务截止约束。`Retry-After` 大于剩余预算时结束等待并报告，而不是提前于服务端要求重试。有限个请求串起来仍可能很长，因此顶层运行另受 R6 限制。

**R5b：**用户可配置有限回退链（建议最多 3 个候选），未配置不跨模型/提供方。绑定 provider+endpoint+model+能力版本，不能仅按同名模型取凭据。候选先检查工具、图片、上下文、结构化输出与已有消息格式是否可承载；不能静默丢附件或剪掉必要结果后切换。

回退前适配窗口与压缩预算；压缩自身失败使用同一有限策略，防止递归回退。模型请求可以重试，外部副作用工具不可因整轮重试再次执行。流中断时保留已提交消息与 tool-use ID，未完成调用标为中断/未知；不能把不确定的执行状态当成可安全重放。实际模型变化写入现有消息/trace 状态，不修改原始历史。

**验收：**429/529/5xx、无效凭据不反复重试；长 Retry-After；取消中断；小窗口回退；同名跨 provider；thinking/图片能力差异；压缩失败；流已产生 tool_use 后掉线。用计数器验证不会再次产生副作用。

**默认/回滚：**新建运行使用有限等待，已有在途运行沿用其固定策略直到结束；回退链默认关闭。可禁用回退，重试到期状态和真实模型记录仍可读。界面可以手动重试模型请求，但不以“重试”为名自动重跑整轮工具。

### R6：统一资源归属，保留现有编排语义

落点：[SessionRuntime](../src/utils/sessionIdContext.ts)、[AgentTool](../src/tools/AgentTool/AgentTool.tsx)、[runAgent.ts](../src/tools/AgentTool/runAgent.ts)、WebSearch/Bash/后台任务入口、Workflow App 的 limiter/agent adapter。预算在实际执行 Host 的 session runtime 内实施，调用者不能通过模型参数另开一份预算；复用现有上下文和任务生命周期。

**必须区分已有机制：**[query/tokenBudget.ts](../src/query/tokenBudget.ts) 是“达到用户指定 token 目标前继续工作”的逻辑，不是资源上限；Workflow limiter 约束节点并发；WebSearch 单请求 `max_uses` 不代表整个会话累计预算。这三者继续有各自语义。

**R6a：计量与观察。** 只补已缺少的运行关联和统计。分别记录活跃 Agent 槽位、累计派生次数、实际可观测搜索消耗、托管后台任务、输出缓存字节、elapsed/deadline。一个顶层用户任务及其子 Agent/Workflow 共享预算归属；后续普通对话不应因长期会话历史累积而永久耗尽。另有“整个会话累计配额”时必须独立配置。

**R6b：约束。** 获取配额与创建资源原子关联；失败/完成/取消释放并发槽位一次，累计消耗不退回；取消后禁止新派生。预算额度由 Host 解析，子任务不能自己提高。Workflow 局部并发受父级总约束，获取顺序固定，父节点等待子节点时不得占满所有执行槽导致死锁。已有后台任务结束前，其额度归属不因下一轮聊天开始而重置。

提供方若不返回真实搜索次数，记录可确认调用数或预留上界，不能假装精确计费。重启后从已有任务/进程记录校准活跃项；无法确认的运行标为待核对，不立即释放后自动重跑。重启和恢复不会自动续做未明确启用的长任务。

**验收：**并发派生竞争；父子嵌套与 Workflow 等待；创建失败；双重完成事件；Stop 后启动竞争；切会话不串账；恢复不重复扣费/放大额度；后台任务跨回合；所有入口统一执行取消。到限后给出已完成、未完成和可恢复条件，不能宣称目标已达成。

**默认/回滚：**新统计可关闭；强制策略先用于显式选择的运行模板，旧任务保持原有限制。停用强制约束不删除账本和任务，不改变 Team 名称、权限继承、前后台默认行为。

落点：[self-test 文档](../ui/docs/self-test.md)、[app-testing](../ui/src/app-testing/host.mjs)、[成对基准脚本](../ui/scripts/benchmark-self-test-paired.mjs)，邻仓 Self-test App 的 catalog、recipe、review、report。已有隔离实例、证据来源校验、环境指纹和版本对照入口直接复用。

- 从首个修复 PR 开始登记确定性契约用例，不等到全部迁移后才做“大自测”。只对新的跨层行为补场景，已有等价用例直接复用。
- 新增场景 ID、验收断言和产物证据；固定 workspace fixture、模型/提供方标识、App/Skill/工具契约版本和运行配置。不能仅以 commit 标识当前脏工作树，需附构建或相关内容指纹。
- 测试分成确定性状态/协议断言、真实 Host 交互、真实模型任务三类。脚本模型用于稳定边界测试；真实模型用于理解、调用与产物质量。真实模型失败保留原始结果，复测单列，不拼成一次全绿。
- 指标优先是任务产物正确性、重复副作用次数、资源泄漏、恢复/取消状态；再看 token、耗时和费用。未知 token/费用明确未知，模型评分与可执行断言分开。
- Skill 对比使用同一任务在启用/禁用或两版本间成对运行；调用率和任务成功率不能混用。不假定已恢复上游 plugin eval 的完整评分器。

默认按需执行，不在每次聊天后台启动评测。首批 fixtures 不需要真人凭据或用户业务数据；涉及真实提供方的费用只来自明确启动的测试。关闭新增场景不影响现有 self-test 和历史报告。

## 6. 模型提示与工具边界怎么迁

上游可以借鉴的是“结构化状态 + 简短工具说明 + 运行时执行约束”。不复制整份新 system prompt；prompt-audit 等压缩资源尚未完整还原，不宣称拥有最新版完整提示词。

下面是 **Moss 拟新增/修改的说明语义**，不是从 Claude 内部逐字提取的提示：

| 场景 | 给模型的短说明 | 必须由本地实现保证的事 |
| --- | --- | --- |
| 搜索/读取 | 结果为 partial 或 count 不完整时，只能描述已返回部分；可使用分页继续读取 | 错误、计数、截断与续读引用真实；提示不能代替检测 |
| `allow_large` | 仅在确需全文且预算允许时请求；拒绝后使用范围读取 | 硬读取上限、上下文余量和取消 |
| 大输出落盘 | 根据 `complete/truncated` 描述全文或片段，并使用返回的有效引用读取 | 不把未完整保存的数据标为全文，不生成无效路径 |
| MCP 刷新 | 仅更新已连接服务目录；失败说明旧目录可能过期 | 不隐式重连、不清空旧快照、不切换在途调用 |
| 侧问 | 根据当前上下文回答；工具执行中不代表成功；侧问不能执行工具 | 运行时禁止工具，维护配对和独立取消 |
| 展示 | 只有回执 shown 才描述为已打开；其余准确描述为已登记或等待展示 | 回执由 Host/renderer 产生，用户关闭/固定拥有优先权 |
| 预算/重试到期 | 陈述当前已完成内容、未完成项及停止原因 | 到限停止派生/请求；不让模型凭一句“继续”绕过 Host 限制 |

R1–R8 大多数改动只需更新现有工具 schema、Host 状态及工具说明，**第一阶段无需批量增加“标准工具”**。诊断优先是 UI/Trace 入口，队列由宿主管理；后续只有 Goal/Monitor 或确实需要模型主动触发的 MCP 刷新，才增加小而明确的动作。

## 7. 实施批次与退出条件

每个编号代表独立可审阅变更；跨仓变更固定 App/SDK 兼容版本。开发开始前选定当前工作树基线，包含既有未提交改动并记录内容指纹；对正在修改的模块先重新确认，避免覆盖。该计划不要求现在提交或重置任何文件。

| 批次 | PR 拆分与交付 | 依赖 / 通过条件 |
| --- | --- | --- |
| A：先得到可见收益 | H1 搜索修复；H2 图片边界；H3 上下文；R2a 完整回填；R1a 搜索计数与 `-o`（分别提交） | H1–H3 原故障探针改成修复断言；三类写文件/打招呼/草稿保留通过。R1a 依赖 H1。此批不启用长期执行或自动回退 |
| B：完善高频工具与连接器 | H4 校验探针及修复；R1b 持久化上限/元数据；R1c 文本扩大读取和网页续读；R3 目录版本与刷新（先契约后 Host/UI） | R1c 依赖 H3/R1b；R3 在现有 MCP 改动上增量实施。同名改 schema、分页失败和活跃调用验收通过 |
| C：可解释与可恢复 | R4a 来源诊断；R5a 重试上限；R2b 回执与恢复（Host 协议、客户端分提交）；R7a 侧问 | R4a 可独立推进；R2b 在 R2a 后；确认丢失和中途取消均不会盲重发；未知状态可解释 |
| D：复杂任务约束 | R6a 只计量；R6b 按模板强制；R5b 自选回退链；R4b 诊断建议 | R6b 依赖 R6a、R1b、R5a 与 H4；R5b 依赖 H3/R5a，副作用恢复相关场景复用 R2b。Team/Workflow 原有行为不倒退 |
| 持续验收 | 每批复用 R7b 展示场景、R8 自测入口补本批用例 | 确定性契约先通过，涉及 UI 的变更做真实 Host 验证；真实模型检查只针对有新风险的路径，不每次重跑全部功能 |
| E：可选长任务试点 | Goal 与 Monitor 各一条最小实现；空闲订阅等另行按需求选 | A–D 的生命周期/预算/恢复基础稳定，有明确场景后开展；不默认全部启用 |

阶段 E 的最小范围：

1. **Goal** 作为已有 Task 的可选执行属性，记录用户确认的完成条件、运行预算和停止条件；接入同一个调度驱动。已有 token 续做与 Goal 只能由同一个状态决策器驱动，不能同时各自追加“继续”。完成要有可检查证据；用户暂停、等待信息、失败和预算耗尽分开。重启只恢复状态，是否继续遵守此前显式策略。
2. **Monitor** 先提供一个本地命令事件源，接既有进程服务、事件队列和任务列表；设事件 ID/去重、节流、最大输出、到期与取消。事件 payload 作为外部数据，不能扩大执行权限；到期/断线不报告为目标成功。重复事件最多触发一次已登记的后续动作，不靠重新跑整个会话完成去重。
3. 两者分别试点“测试完成后汇报”和“固定目标检查到满足条件”；先只报告，不自动发布或外发。验收 Stop、重启、重复事件、用户改目标、预算耗尽和多个任务同 workspace。没有实际收益或恢复不稳定时保留为手动/关闭，不进入默认聊天。

## 8. 统一兼容与验收底线

| 场景 | 要保持的结果 |
| --- | --- |
| 无 `.git` 的 workspace | 功能可用，不执行 `git init`；原内部版本存储与用户仓库分离。系统无 Git/观察覆盖不足如实呈现，不写“完整零变化” |
| 原本存在未提交改动 | 文件观察基线含已有内容；不将全部脏文件算作本轮生成，不自动丢弃用户修改 |
| Write/Bash/Python/外部程序修改 | 相同观察口径；可说明期间变化，不能声称全部是某个工具的贡献 |
| 旧 transcript、旧 Host/App | 新字段可选、能力协商、未知态可读；不得用缺失字段推断成功、总数 0、已打开或可撤回 |
| Desktop / Web / remote-direct | 在实际执行 Host 保存权威状态；路径、模型凭据、workspace 和资源归属保持隔离；不支持能力明确返回，不伪装本机路径可用 |
| 多提供方与网关 | fixture 覆盖不同上下文、流/非流、工具/图片及错误格式；至少在原生 Messages 与 OpenAI 兼容路径分别验证相关行为 |
| Team/Boss/Coordinator/Workflow | 默认前后台、权限、任务归属和 Definition 语义保持原样；预算与状态是增量能力 |
| Task list/右侧工作区/结果 | 一份任务状态与资源记录，多个入口复用；工具折叠不会复制任务或吞掉成果入口 |
| 取消、崩溃、恢复 | 无新派生、无静默盲重放；已发生但结果未确认的副作用保持未知/待核对，不以自动重试掩盖 |

交付每批需附：改动范围、行为前后对照、针对性测试结果、仍未支持的环境、默认开关及回滚方式。真实模型指标按同一环境成对比较，报告样本量和原始失败；不以一次成功声称稳定性改善百分比。

最终取舍是把最新 Claude Code 的**状态与结果语义、低成本交互改进、可诊断性和运行边界**迁入 Moss。日常使用先受益，持续自治随后建设；Moss 自己的 Workspace 与 App/Workflow 架构继续作为承载层。
