Moss 云端空间分阶段实施计划，更新于 2026-09-23。

本文记录已讨论确定的开发范围、实施顺序和验收标准。本期六阶段已完成。数据库重构后，SQLite/MySQL 回归、本机 ARM64 源码镜像构建、独立 Compose 部署、真实 HTTPS 大文件传输、Electron Host、备份恢复和重复部署均已验证。分享仍为后续独立阶段。

本期交付一套可供 App 使用的公共云端存储能力：默认随 moss-server 部署 Silo，由 moss-server 使用 S3 协议访问存储、统一鉴权并代理文件传输；Moss Host 提供 `moss.cloud-storage/v1`。

既有 App 的 `storage.json`、Backend `dataDir`、本地资料库、会话工作区及 OpenIM 存储维持原有逻辑。用户或获授权的 App 显式发起上传后，文件才进入云端空间。

职责固定如下：

| 部分 | 本期职责 |
| --- | --- |
| 部署脚本 | 部署 Silo，创建私有 bucket、服务账号和策略，生成并保存 S3 配置 |
| moss-server | S3 对象读写、文件目录、用户鉴权、权限、配额、上传会话、文件传输及失败恢复 |
| Moss Core / Host | 公共协议、App 权限检查、账号连接适配、文件选择、传输任务及进度事件 |
| 后续网盘 App | 文件浏览、操作和传输队列等产品界面 |

Silo 的初始化管理代码只放在部署流程中。Core 不包含存储厂商初始化逻辑、S3 凭证或网盘 App 专属逻辑。moss-server 的日常文件操作只使用受限的 S3 服务凭证。

访问链路为 `App → Moss Host → HTTPS/Nginx → moss-server → 内网 S3/Silo`。Silo 不发布主机端口，客户端无法直接调用 S3，也不接收重定向到 S3 的地址。

实施顺序为阶段 1 至阶段 6。每个阶段应交付可以单独评审的变更，并完成该阶段验收。

| 阶段 | 主要交付 | 完成标志 |
| --- | --- | --- |
| 1. 接口契约与数据模型 | HTTP/Host 契约、文件模型、权限及状态规则 | 本期行为和兼容性边界明确，可据此实现 |
| 2. Silo 自动部署与 S3 连接 | 安装初始化、配置、凭证、薄 S3 适配层 | 安装后自动连通，重复安装和升级保留配置 |
| 3. 服务端文件管理与用户隔离 | 元数据持久化、目录操作、鉴权、配额 | 用户可管理自己的目录，跨用户请求被拒绝 |
| 4. 大文件传输与恢复 | 分片上传、Range 下载、清理和对账 | 多 GB 文件可重试、续传并经受服务重启 |
| 5. Host 公共云端能力 | SDK、能力注册、传输管理、远程状态处理 | App 通过公共 API 完成文件操作和任务控制 |
| 6. 联调、打包与交付 | 最小接入示例、端到端验收、发布及恢复文档 | 从干净部署到 App 调用的完整链路通过验证 |

**阶段 1：接口契约与数据模型。** 固定业务边界和失败行为，避免服务端与客户端各自解释接口。

工作项：

- 定义 HTTP 前缀 `/api/v1/cloud-storage` 和 Host 协议 `moss.cloud-storage/v1`。
- 定义服务状态、文件信息、上传会话、传输任务、分页和错误码。
- 定义组织和用户名下的个人云端空间，以及文件、文件夹、上传会话和分片的数据模型。
- 对外使用稳定的 `fileId`；数据库记录所有者、父目录、对象位置、内容版本及文件状态。文件名和目录关系独立于 S3 对象 key。
- 定义统一的文件授权入口。首期检查组织、所有者、当前用户状态及有效权限；管理员身份不自动绕过文件归属检查。
- 默认同目录同名返回冲突。首期上传创建新文件，覆盖写入留到显式接口设计后扩展；文件夹禁止移入自身或子目录，删除非空文件夹返回明确错误。
- 内容版本用于续传与一致性校验，不实现历史版本归档。首期不提供自动同步和隐式本地回退。
- 首期只配置一个 S3 后端；保留实际对象定位信息，不实现多后端路由、在线迁移或存储插件框架。切换到另一个实际存储需要先迁移并校验对象；未完成上传期间不允许直接切换存储目标。

HTTP 契约范围：

| 接口 | 用途 |
| --- | --- |
| `GET /status`、`GET /quota` | 状态与容量 |
| `GET /files?parentId=…&cursor=…`、`GET /files/:id` | 文件列表与详情 |
| `POST /folders` | 创建目录 |
| `PATCH /files/:id` | 改名或移动 |
| `DELETE /files/:id` | 删除文件或空目录 |
| `POST /uploads` | 初始化上传 |
| `PUT /uploads/:id/parts/:number` | 上传分片 |
| `GET /uploads/:id` | 查询上传状态和已完成分片 |
| `POST /uploads/:id/complete`、`DELETE /uploads/:id` | 完成或取消上传 |
| `GET /files/:id/content`、`HEAD /files/:id/content` | 下载及内容响应信息 |

验收：契约包含用户身份来源、资源归属检查、同名冲突、分页、错误、删除和续传规则；本地数据与云端空间的关系没有隐式切换或迁移。

**阶段 2：Silo 自动部署与 S3 连接。** 交付默认可用的服务端存储环境。

工作项：

- 默认镜像固定为 `docker.1ms.run/pgsty/silo:RELEASE.2026-08-06T00-00-00Z`，通过 `MINIO_IMAGE` 配置；Silo 版本独立于 Moss 发布版本管理。
- Compose 使用独立存储网络和持久化目录。内部服务地址默认为 `http://silo:9000`，bucket 默认为 `moss-cloud-storage`，使用 path-style，显式配置 region。
- 脚本启动 Silo、等待服务就绪、创建私有 bucket、受限服务账号和策略，写入 S3 连接参数。管理凭证只用于初始化管理，moss-server 运行时使用服务凭证。
- 明确初始化工具及版本，实际验证指定 Silo 镜像的管理能力，不假定镜像自带 `mc`。
- 首次安装自动配置；重复执行、重启和升级复用已有凭证，保留用户调整过的连接及显式禁用配置。中断的初始化可重试。
- 新增 `cloudStorage` 配置，避免与服务器本地路径配置 `storage` 混用。非敏感连接参数只有一个配置来源，服务凭证复用 `ServerCredentialStore`；部署参数与运行连接参数各自明确职责。
- 外部 S3 使用提供的 bucket 和凭证，只验证数据操作能力，不执行 Silo 账号和策略初始化。
- 服务端使用 AWS SDK for JavaScript v3，薄封装对象信息、读取、写入、删除及 Multipart 操作。
- 初始化完成后执行限定测试对象的写入、读取、删除和分片探测；失败时云端存储保持未就绪，其他 moss-server 功能可继续运行。

主要位置：`deploy/server/`、`server/src/config.ts`、`server/src/types.ts`、`server/src/security/credentialStore.ts`，以及新增的 `server/src/cloudStorage/`。

验收：干净安装可自动连接；公网没有 Silo API 或控制台入口；重复初始化不换账号、不覆盖配置；管理凭证不会进入 Core 或 App；指定镜像的基本 S3 能力经过真实容器验证。

**阶段 3：服务端文件管理与用户隔离。** 完成个人云端空间的元数据和授权。

工作项：

- 使用统一的异步 model 层和可重复执行的数据库迁移；Compose 默认 MySQL，保留 SQLite 调试与测试支持。
- 实现空间、文件与目录的持久化，以及列表、详情、创建目录、改名、移动和删除接口。
- 使用 `orgId`、`ownerUserId` 和服务端生成的对象 ID 组织对象 key。客户端不能指定任意 bucket、对象 key 或其他用户的目录。
- 列表、详情、目录操作、上传会话及内容访问均走统一授权入口。移动操作同时检查源和目标；上传中的目标目录被删除或移动等并发情况必须有确定结果。
- 云端权限独立定义为 `cloud-storage:read`、`cloud-storage:write`、`cloud-storage:delete`。用户状态、当前有效权限及凭证有效性都参与校验。
- 实现基本配额、已用与预留容量的事务更新，为阶段 4 的并发上传提供正确性保障。
- 文件删除先变为不可访问，再清理对象；清理失败可重试，容量释放规则与对象清理保持一致。

验收：两个用户及两个组织的请求互相隔离；替换 `fileId`、`parentId` 等参数不能越权；同名、非法移动和非空目录删除行为符合契约；列表只返回当前可访问且可用的文件。

**阶段 4：大文件传输与恢复。** 全部文件字节经 moss-server 网关传输。

工作项：

- 初始化上传时检查目录、大小和配额并预留容量；返回上传会话、分片大小和过期时间。
- 初始采用 16～32 MiB 分片、3 路客户端并发，根据文件大小和 S3 限制确定最终参数；每个分片均重新鉴权并核验实际接收大小。
- 分片经有界缓冲流式转发到 S3。服务端不透明重放已经消费的请求流；由客户端重试对应分片。
- 初始化和完成操作支持幂等。完成前核对 S3 实际分片、总大小及校验信息；确认对象成功后发布文件记录。Multipart ETag 不作为整个文件的 MD5。
- 上传状态包含上传中、完成处理中、可用或失败清理等必要状态。处理 S3 已完成而数据库尚未更新、完成响应丢失、重复完成及取消与完成竞争等情况。
- 后台清理过期 Multipart、失败对象和删除待清理对象；恢复处理中状态，避免误清理仍活跃的上传。
- 下载支持 `HEAD`、`Range`、`206`、`416`、`Content-Length`、`Content-Range` 及稳定内容版本校验。续传文件变化时明确失败或重新开始，不能拼接不同版本。
- Nginx 关闭云端上传请求缓冲；明确分片体积、Node/Nginx/S3 超时、全局及每用户并发上限。连接取消要传递到上游 S3 请求。
- 处理空文件、上传源变化、目标存储空间不足和上传会话过期等边界。

验收：真实 Silo 上完成多 GB 文件上传和下载并校验内容；断网后只重传缺失分片或继续下载；服务重启、重复请求及完成中断不会产生重复文件或永久占用配额；内存占用随受控并发增长，不随文件总大小线性增长。

**阶段 5：Host 公共云端能力。** App 使用统一接口，传输由宿主管理。

工作项：

- 在 `packages/app-sdk` 定义协议、方法、类型、校验和权限；在 `packages/app-runtime` 注册能力，并由桌面 Host 提供处理器。
- Host 只接受当前调用 App 的上下文并检查其声明和授权，不接受 App 自行覆盖用户身份。服务端继续负责实际资源授权。
- 增加公共的本地文件选择和授权句柄机制，支持大文件直接读取，避免将整份文件预先复制进 App 缓存；原有平台文件接口维持原语义。
- 新增专用传输管理器。创建任务立即返回 `transferId`，文件字节通过 HTTP 流传输，不经 Host JSON/Base64 通道。
- 任务持久化在新的云端传输目录或数据库中，绑定服务器连接、组织、用户和 App；不使用 App 的小容量 `storage.json` 存放传输状态。
- 支持进度、有限重试、暂停、恢复、取消和任务查询；下载写入临时文件，成功后改为目标文件名。
- 关闭 App 窗口时 Host 可继续任务；禁用或卸载 App 后停止该 App 的传输；退出 Moss 时保存恢复信息。
- 账号切换、退出或权限撤销时停止旧任务；恢复前重新鉴权并检查源文件及目标版本。旧请求不能改用新账号的凭证。
- 远程关闭时不发起云端请求；未登录、服务端未启用、不支持、不可达和就绪分别返回明确状态。Agent 的本地/远程运行位置不决定存储位置，云端失败不回退本地写入。
- 增加服务端能力发现和 Host API 次版本兼容声明，旧 App 按原协议继续工作。

Host 方法范围：

| 方法 | 用途 |
| --- | --- |
| `status.get`、`quota.get` | 可用状态和容量 |
| `files.list`、`files.get`、`folders.create` | 文件查询和目录创建 |
| `files.update`、`files.delete` | 改名、移动、删除 |
| `local-files.pick` | 选择待上传文件并返回受控句柄 |
| `uploads.start`、`downloads.start` | 创建任务并立即返回任务 ID |
| `transfers.list`、`transfers.get` | 查询任务 |
| `transfers.pause`、`transfers.resume`、`transfers.cancel` | 控制任务 |

事件包括 `transfers.progress`、`transfers.changed` 和 `storage.status-changed`。进度推送应节流，重新订阅后可通过任务查询获得当前状态。

主要位置：`packages/app-sdk/`、`packages/app-runtime/`、新增桌面云端服务模块，以及 `ui/src/main.mjs` 的能力注册与设置变化接入点。

验收：最小 App 能通过公共 API 完成选择文件、上传、列表和下载，观察进度并控制任务；账号切换、远程关闭和 App 禁用不会越权续传；Host RPC 不等待整份大文件完成。

**阶段 6：联调、打包与交付。** 交付可复现的安装和使用链路。

工作项：

- 提供最小 App 接入示例或验证夹具，覆盖 Host API 和事件，不在本期开发完整网盘产品界面。
- 运行服务端、SDK 和 Host 对应的类型检查、针对性测试，以及部署脚本验证。
- 使用指定 Silo 镜像执行端到端验证，覆盖新安装、重复安装、升级保留配置和初始化失败重试。
- 验证跨用户和跨组织隔离、源文件变化、并发配额、断网恢复、账号切换、服务重启、删除重试及版本变化后的续传处理。
- 验证既有 App 数据、本地资料库、会话工作区及 OpenIM 操作没有因新增能力改变。
- 补齐 SDK 接入文档、配置说明、故障状态说明、S3 更换流程及发布兼容说明。
- 提供单机备份与恢复步骤，覆盖元数据数据库、对象、配置、服务凭证和加密主密钥；恢复后验证列表和文件下载。备份需要采用明确的一致性方案，例如暂停写入及清理后制作备份。

验收：从干净环境安装到 App 完整上传下载的流程可重复；失败场景有明确状态和恢复路径；备份恢复后的文件内容校验通过。全部通过后，本期公共云端空间能力才算交付完成。

**后续阶段：单文件只读分享。** 本期只保留稳定文件 ID、内容版本、所有权和统一授权入口，暂不创建完整分享权限体系。

后续按需要增加指定用户授权或分享链接，提供有效期、撤销和只读权限。分享凭证及授权记录保存在 moss-server，文件保持原所有者和对象位置，访问仍经过网关。分享链接入口使用专门的分享凭证校验，普通文件接口维持登录鉴权。

Core 只扩展通用的 `shares.create`、`shares.list`、`shares.revoke` 等 Host 方法；分享弹窗、链接展示和接收页面由 App 实现。届时明确文件删除、内容变化和分享撤销后的行为；文件夹分享、权限继承与协作编辑另行设计。
