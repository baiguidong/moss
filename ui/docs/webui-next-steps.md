# WebUI 后续执行计划

更新：2026-10-16。目标是用户通过浏览器进入自己的长期 Linux 环境；Agent 在此环境内按本地模式运行。Moss Server 暂以认证为主，保留既有会话接口，不新增会话运行链路。完整架构见 [设计文档](desktop-webui-cloud-environments.md)。

## 当前版本的部署约束

- 一份 WebUI 实例只属于一个用户。Server 安装默认关闭 WebUI，`MOSS_WEB_ENABLED=1` 启用；管理员解析/显式用户 ID 确定归属，不能由第一个浏览器访客认领。
- WebUI 使用独立 HTTPS 端口和独立 HOME 卷；只连接 Server 的现有认证 API。应用容器没有宿主机 Docker socket。
- 正常 `start`、`stop` 和 Server 升级保留原 WebUI 容器。修改镜像标签不会自动替换该容器；已运行实例的用户/来源配置不匹配时直接报错，避免错误归属。
- HOME 卷保留会话和用户文件；apt 与 /etc 仍位于容器写层。镜像包仅包含程序及基础工具，不包含个人系统备份。
- 这一阶段不提供“升级镜像即可保留任意系统安装”的承诺。2A 通过之前不自动重建个人环境，不开放批量多用户自动创建。

## 下一轮首先交付什么

先完成 2A-1 的单用户系统恢复原型，并保留现有 Docker WebUI 作为应用交付格式。优先评估 Incus/LXC 的持久化根文件系统；若部署条件或隔离要求不适合，改用 VM/微虚拟机系统盘。接口只覆盖 create/start/stop/inspect/snapshot/restore，不提前引入集群调度。

若继续使用普通 Docker，需要明确保存系统层、用户卷一致性和恢复点；`docker commit` 单独不构成完整备份。新建用户平台不得先绑定到仅有临时容器写层的存储方案。

恢复验收使用真实安装：一个 apt 包、Python venv、Node CLI、/etc 配置、Moss 会话、附件与一份测试凭据。依次测试重连、停启、程序升级、替代实例恢复；每一步记录能恢复的内容与正在运行进程的中断语义。

## 发布验收

`gh workflow run build-release.yml` 触发独立 AMD64 WebUI 构建；完整版本的 `release.yml` 复用同一流程。独立构建默认只推送指定版本，稳定完整发布才更新 latest。检查构建元数据、健康检查、浏览器本地执行、权限确认刷新恢复、WS 重连去重、PTY、同容器重启以及无 Electron renderer。

支持 Server 一键安装表示复用认证、代理与部署脚本；不表示已实现统一多用户门户。正式多用户接入之前必须通过 2A 与归属隔离验收。
